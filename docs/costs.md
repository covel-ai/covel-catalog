# 部署取舍与费用估算

核对日期：2026-10-29。美元/月、按 30 天估算，不含税、域名、人工运维和独立备份。本仓当前实现的是 Node/SQLite/本地文件方案；下面的 Cloudflare 数字是迁移后的模型，尚未实现或开通该服务。

[可调整 CPU 假设的图表](cost-estimate.html)

## 当前决定

先用一个 Docker Compose 服务，SQLite 保存目录快照、版本账本、规则和计数，私有磁盘保存 ZIP。两个 GitHub Pages 站点共用 `api.covel.cc`。已有合适服务器时，新增固定计算费用可接近 $0，但磁盘、流量、备份和运维仍有成本。

新购服务器可将 **2 GiB 内存、1 vCPU、50 GiB 磁盘约 $12/月**作为预算参照；这不是负载容量保证，也不能把容器的 2 GiB 上限当作实际常驻内存。操作系统需要余量，多个大包同时打包时应测量 RSS，必要时升配。参照 [DigitalOcean 官方基础实例价格](https://www.digitalocean.com/pricing/droplets)。

## 1,000 用户和 1,000 仓库的两种含义

目录规模不等于用户请求量。24 条摘要一次返回；采集 GitHub 与访客请求解耦。1,000 仓库每六小时核对一次是每天约 4,000 次仓库观测，每次还可能有多个 API 请求；不会为每位访客重新抓取全部 GitHub 仓库。

| 场景 | API 请求/天 | API 请求/月 | Workers 付费模型/月 |
| --- | ---: | ---: | ---: |
| 1,000 人，每人每天 20 次 API 请求 | 20,000 | 600,000 | $5 |
| 1,000 人，每人看完 1,000 条摘要，24 条/页 | 42,000 | 1,260,000 | $5 |
| 1,000 人，每人每天 1,000 次独立请求 | 1,000,000 | 30,000,000 | $11.60–16.40 |

以上仅计元数据请求，假设平均计费 CPU 为每请求 2–10 ms（已经考虑缓存后的平均值，尚无实际 Worker 测量）。付费公式为 `5 + max(请求数-1000万,0)/100万×0.30 + max(请求数×平均CPU毫秒-3000万,0)/100万×0.02`。免费版每天 10 万次、每次 CPU 上限 10 ms；前两行可能落在免费额度内，但必须同时满足 CPU、D1 和存储约束。缓存命中的请求仍计请求费用，主要节省 CPU/数据库工作。[Workers 官方价格](https://developers.cloudflare.com/workers/platform/pricing/)

## 缓存、数据库和下载

D1 按扫描行数计费，不能只看 API 次数。免费额度每天读 500 万行、写 10 万行；付费包含每月读 250 亿行、写 5,000 万行。假设第二行场景有 90% 摘要缓存命中，每个 miss 读 24 行，另每请求读一行策略版本，则约 `42,000×10%×24+42,000=142,800` 行/天，索引、计数及其他查询另计。这个模型要求索引查询和增量写入，不能原样迁移当前整份快照解析。两种目录各 1 万条、每天全量写四轮，基础写入已达 8 万行，尚未计索引和账本。[D1 官方价格](https://developers.cloudflare.com/d1/platform/pricing/)

免费 D1 每库上限 500 MB、账户合计 5 GB，单行 2 MB。历史与索引需要容量预算，整份大 catalog 不能放在单行中。[D1 限制](https://developers.cloudflare.com/d1/platform/limits/)

R2 Standard 每月含 10 GB 存储、100 万次写类操作和 1,000 万次读类操作，出网免费。额外存储 $0.015/GB·月：例如 50 GB 总存储约 $0.60/月，另计超额操作费。假设 1,000 个包，每包 5 MB、保留三个版本，约 15 GB；仓库数不等于包数，历史不能无界增长。每天 2,000 次 5 MB 下载约 300 GB/月出网，R2 不收出网费；签票和取文件仍有网关请求及数据库事务成本。下载量远超此假设时应重新估算。[R2 官方价格](https://developers.cloudflare.com/r2/pricing/)

所有统计保持现有口径：只有可用产物通过规则校验并成功签票才计一次 `downloadRequests`；重试、Range 和 HEAD 不重复计数。ZIP 在私有桶中，每次取文件检查最新撤销规则。不得用长效公开 URL 绕过网关。

## 为什么现在不直接迁移 Workers

当前打包器可读取 200 MiB 包内容；Worker 内存上限为 128 MB，免费 CPU 限制也不适合重打包。未来可把 API 查询放 Workers、账本改 D1、ZIP 放私有 R2，打包交给异步执行器或 GitHub Actions。缓存未命中返回 pending/job，产物完成后再签票。该迁移涉及 SQL/索引、异步队列、身份与规则一致性，绝不是换一个启动命令。[Workers 限制](https://developers.cloudflare.com/workers/platform/limits/)

## 逐步扩容

| 出现的实际瓶颈 | 下一步 | 仍需保持的边界 |
| --- | --- | --- |
| 本机 ZIP 容量或流量压力 | 先换私有 R2/S3 兼容对象存储 | 对象按 hash 寻址；取文件前实时规则检查 |
| 打包挤占 HTTP 响应时间 | 独立打包进程和持久任务队列 | single-flight、失败重试、固定 SHA，不执行包脚本 |
| 多实例需要共享队列/速率限制 | 引入 Valkey 或其他共享协调组件 | 不能把缓存当版本账本；SQLite 不能直接跨主机共享写 |
| 写竞争或数据规模超过单实例 | 测量后迁移事务数据库及索引查询 | 历史映射、幂等计数和撤销规则的事务约束不变 |

[Valkey](https://github.com/valkey-io/valkey) 可用于分布式缓存/协调；现在已有单进程队列和 SQLite 事务，没有理由提前增加常驻服务。自托管 S3 可评估 [Garage](https://garagehq.deuxfleurs.fr/)，但集群副本、磁盘故障和备份会成为自己的运维责任；单机加一个 S3 容器并不会自动获得高可用。首期不附未经集成验证的 Redis/S3 Compose 占位服务。

先观察 API p95、RSS、数据库/产物容量、GitHub 配额与打包排队时间，再决定扩容。当前服务默认每个 socket 来源每分钟 180 次请求；反向代理后会合并来源，公开上线前必须结合流量调整入口限流。上述账单模型不代表当前默认配置已经承载对应流量。
